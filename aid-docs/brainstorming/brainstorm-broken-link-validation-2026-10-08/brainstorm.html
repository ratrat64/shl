Morphological Analysis / timing

Choose the clock before the alarm.

Cadence is a trade between discovery lag, traffic, and recovery speed—not a promise of scheduled service.

Retain the divergence · I001–I010 · 10 timing candidates
  1. I001Run a full scan daily at an off-hour minute; balance discovery lag against request traffic.
  2. I002Run weekly for a rarely edited directory; accept a longer stale-state window.
  3. I003Offer workflow_dispatch for an immediate recovery check after a destination repair.
  4. I004Add an optional exact short-code selector for targeted manual scans, without inventing search syntax.
  5. I005Check changed destinations on PRs in report-only mode; separate external availability from required structural validation.
  6. I006Check changed destinations after human merges to main, filtering out tag-only changes to avoid a feedback loop.
  7. I007Run only on demand initially to measure false positives before choosing a schedule.
  8. I008Spread large directories into daily slices; explicitly accept slower recovery for each slice.
  9. I009Use one checker concurrency group so overlapping scheduled/manual scans cannot race source updates.
  10. I010Expose scan start, completion, source SHA, and checked/unknown/skipped counts in the Actions summary; scheduled execution is best-effort, not an SLA.
02

Morphological Analysis / request contract

Visit the destination. Don’t perform the content.

An HTTP observation is deliberately smaller than a browser visit or a script execution.

Retain the divergence · I011–I020 · 10 request candidates
  1. I011Check destination URLs from the source map, not shl URLs whose HTML forwarding curl does not follow.
  2. I012Use GET as the first-version evidence request; avoid treating an unsupported HEAD as a dead destination.
  3. I013Consider HEAD then GET fallback only if measured bandwidth savings justify the extra state paths.
  4. I014Follow HTTP redirects with a bounded hop count, recording the final URL without retargeting the source.
  5. I015Treat HTML meta refresh and JavaScript forwarding as out of scope for an HTTP-only checker.
  6. I016Cancel or close response bodies after obtaining status to avoid downloading large files or scripts; never execute fetched content.
  7. I017Deduplicate identical full destination URLs within a scan; apply one observation to every matching entry.
  8. I018Do not normalize away query parameters or rewrite URLs; signed URLs and query-specific resources may differ.
  9. I019Check hidden and disabled entries too because discoverability/enforcement are independent of reachability.
  10. I020Use an honest fixed checker User-Agent and no visitor credentials, cookies, or browser impersonation.
03

Failure Analysis / classification

Three signals. Only two may touch the switch.

Conservative classification separates explicit disappearance from a runner’s inability to establish availability.

Retain the divergence · I021–I030 · 10 classification candidates
  1. I021Call final 2xx reachable, not proof that the page content or script works.
  2. I022Require two matching 404 observations within the latest run before proposing broken.
  3. I023Require two matching 410 observations within the latest run before proposing broken.
  4. I024Keep 401/403 inconclusive: authentication, WAFs, geographic rules, and bot denial can differ from visitor access.
  5. I025Keep 429 inconclusive and honor Retry-After within the run budget.
  6. I026Keep 5xx inconclusive in the first version even after retries; server outages are often temporary.
  7. I027Keep DNS, TCP, and TLS failures inconclusive initially; a runner vantage point cannot establish permanent disappearance.
  8. I028Keep redirect loops and hop-limit exhaustion inconclusive initially; report actionable evidence for a maintainer.
  9. I029Treat unusual 4xx, unhandled 3xx, and invalid responses as inconclusive rather than assuming every non-2xx is broken.
  10. I030Report suspected soft-404/content errors for manual review only; detecting them requires content semantics beyond HTTP status.
04

Failure Analysis / budgets and courtesy

A budget is a brake, not a target.

Proposed starting defaults are unmeasured. Every redirect hop participates in origin courtesy.

Retain the divergence · I031–I040 · 10 budget candidates
  1. I031Start with a 15-second total request/redirect-chain deadline, not a fresh full timeout for every hop.
  2. I032Retry uncertain network/server failures once with short jittered delay; a successful retry may clear broken.
  3. I033Give each URL a bounded total evaluation budget such as 45 seconds covering attempts and waits.
  4. I034Cap the whole job, such as 15 minutes; classify unvisited entries as skipped without changing tags.
  5. I035Limit concurrency to four requests globally and one per origin as unmeasured starting defaults.
  6. I036Delay between requests to one origin so a directory with many paths does not become a burst.
  7. I037Parse Retry-After as seconds or HTTP date; malformed values get bounded fallback delay.
  8. I038If Retry-After exceeds remaining budget, stop requesting that origin and report unknown rather than sleeping indefinitely.
  9. I039Back off an origin after repeated 429s; rate limiting must reduce work rather than amplify retries.
  10. I040Attach transport error category, HTTP statuses, retry count, and duration to each observation rather than dumping response bodies.
05

Assumption Reversal / recovery and history

The latest evaluation is not the latest request.

A completed bounded evaluation can contain two attempts. Recovery can win within the run, without durable strike counters.

Retain the divergence · I041–I050 · 10 recovery candidates
  1. I041Replace binary pass/fail with reachable, broken, unknown; skipped is a coverage outcome, not reachability.
  2. I042Clear every case-insensitive broken tag on the latest completed 2xx evaluation, even if a person added it.
  3. I043Preserve existing broken on unknown or skipped; preserve absence of broken on unknown or skipped too.
  4. I044Treat 404 then 200 in one run as reachable; recovery evidence takes precedence over the first failure.
  5. I045Treat 404 then timeout or 500 as unknown, not confirmed broken.
  6. I046Treat 404 then 410 as unknown under strict matching-confirmation rules, unless a later policy explicitly accepts mixed gone statuses.
  7. I047Retry within the current scan to avoid cross-run strike counters and their storage/reset rules.
  8. I048Explore two-failing-days hysteresis only if single-run confirmation proves noisy; it needs durable history, unlike ownership metadata.
  9. I049Explore two-successful-runs recovery only if flapping is common; it delays recovery and requires history.
  10. I050Explain that no ownership tracking means manual broken is not a sticky override; disabled is the separately user-controlled state, not a substitute for broken.

Build on What Works / source edits

One small annotation. The rest stays yours.

Reuse validated leaf interpretation; mutate the source carefully rather than inventing another schema.

Retain the divergence · I051–I060 · 10 source-edit candidates
  1. I051Reuse validated leaf traversal and URL interpretation from src/links.mjs rather than adding a second source schema.
  2. I052Patch YAML through yaml document nodes to retain comments and key order; do not serialize the whole map through plain JSON.
  3. I053Patch JSON structurally, then use existing Prettier for stable output; acknowledge formatting diffs may be wider.
  4. I054Expand a URL-string leaf into an object only when adding broken; a successful untouched string needs no conversion.
  5. I055Remove broken without collapsing an existing object back to a string, avoiding unnecessary shape churn.
  6. I056Match tags exactly after trimming and case folding; never remove descriptive tags like broken-example.
  7. I057Preserve title, script, hidden/disabled tags, descriptive tags, and destination spelling when updating broken.
  8. I058Add canonical lowercase broken only if absent; remove all case variants on recovery without maintaining ownership metadata.
  9. I059Avoid empty tags arrays after removal but preserve unrelated fields; make a second application a no-op.
  10. I060Compare the final formatted source to baseline and create no commit or PR when there is no diff.
07

Failure Analysis / stale results and partial scans

Good evidence has an expiry problem.

A result belongs to an exact source SHA and full destination. A repaired target must not inherit an old verdict.

Publication stop conditions

Main changed; unexpected human commits on the bot branch; crash, parse failure, or cancellation. Stop and report before writing stale or half-finished source.

Partial is not invalid

An ordinary partial scan may propose completed decisive results, with coverage explicit. Skipped links retain state. Broad transport failures are runner/network incidents, not a directory full of proven dead links.

Refresh or withdraw obsolete PR suggestions. Show check age and SHA in the PR; an old human-merged PR is not proof of current destination state. Start with safe stop/report rather than automatic reconciliation or unconditional force-push.

Retain the divergence · I061–I070 · 10 freshness candidates
  1. I061Bind every scan to an exact source commit SHA and full destination URL so an old result cannot silently describe a repaired target.
  2. I062Before pushing, refetch main; if its SHA changed, discard the candidate and rescan on the next run rather than implementing automatic reconciliation first.
  3. I063Updating an open bot PR from newer main must recompute the desired diff, never replay an old whole-file patch.
  4. I064Prefer a stop-and-report rule when the bot branch contains unexpected human commits; never overwrite collaborative work blindly.
  5. I065If a bot PR ages beyond the next scan cadence, refresh its evidence before treating it as current.
  6. I066On checker crash, parse failure, or cancellation, publish no source updates from a half-written local file.
  7. I067After an ordinary partial scan, allow completed decisive results into a proposed PR but label coverage explicitly; skipped links retain state.
  8. I068Detect a broad transport failure and report a runner/network incident instead of presenting many individual unknowns as dead links.
  9. I069Expose a stale-check age in the PR description instead of inventing last-checked fields on every link.
  10. I070If a previously proposed change is no longer supported, remove it from the bot PR or close a now-empty PR rather than merging outdated evidence.

Morphological Analysis / committing and credentials

The scan-to-PR-to-Pages relay.

Keep the checked-in map authoritative. Publishing evidence is not the same as publishing a site.

The token nuance matters

As recorded from GitHub docs fetched 2026-10-08: GITHUB_TOKEN pushes do not trigger push workflows. Bot PR opened/synchronize/reopened events now create approval-required workflow runs, rather than being described as universally absent.

App/PAT events can trigger automatically; workflow_dispatch and repository_dispatch are exceptions to suppression. A direct GITHUB_TOKEN write to main needs permitted branch rules and explicit deployment dispatch. App/PAT writes can trigger deployment but still need a bypass if main requires PRs. Actual repository rules/settings have not been inspected.

Retain the divergence · I071–I080 · 10 publishing candidates
  1. I071Use a scheduled/manual checker to propose a bot PR; human merge keeps the established source-of-truth and Pages path.
  2. I072Start with GITHUB_TOKEN plus contents:write/pull-requests:write only for the checker publisher, subject to repository settings allowing PR creation.
  3. I073With GITHUB_TOKEN bot PRs, document the current manual Approve workflows to run step for PR validation.
  4. I074Use a GitHub App installation token when unattended PR checks and automatic updates justify credential setup.
  5. I075A scoped PAT is a smaller setup alternative to an App but has person-bound credential lifecycle; evaluate only if needed.
  6. I076Direct GITHUB_TOKEN commits to main require branch rules to permit them and explicit deployment dispatch; ordinary push will not start Deploy shl.
  7. I077App/PAT direct writes can trigger deployment normally but still conflict with a PR-required main policy unless an explicit bypass is configured.
  8. I078Auto-merge bot PRs only as a separately chosen policy after required PR validation passes; external checks should not become a bypass for structural CI.
  9. I079Avoid deploying uncommitted mutated dist output because the live site could diverge from the checked-in link map.
  10. I080Commit only the source-map diff with a concise bot message; keep status evidence in summary/PR/artifact, not an expanding committed history file.

Ship in 60 Minutes / minimal rollout

Earn automation one step at a time.

The technique’s name is a constraint, not a delivery-time estimate.

Retain the divergence · I081–I090 · 10 rollout candidates
  1. I081Begin with report-only manual scans and a few representative destinations before enabling source writes.
  2. I082Add daily plus manual checks only after the report-only results demonstrate reasonable classifications.
  3. I083Keep destination availability outside required PR validation so an unrelated external outage cannot block a legitimate edit.
  4. I084Use Bun fetch and the installed yaml package; no browser farm, crawler library, service, or database in version one.
  5. I085Keep checker network logic separate from tag mutation so fake HTTP results can verify policy without real websites.
  6. I086Preserve the existing deploy workflow; a human-merged bot PR should trigger the ordinary push-to-main deployment.
  7. I087Use one pending bot PR to avoid a daily queue; update only a clearly bot-managed branch and avoid unconditional force pushes.
  8. I088Default publisher failure to a failed workflow and retained report, never to a fallback direct write to main.
  9. I089Provide a dry-run mode using exactly the same classification/mutation calculation as write mode.
  10. I090Defer cross-run caches, adaptive schedules, content inspection, and per-domain exception config until actual false positives or traffic justify them.

Worst Possible Idea / inverted shortcuts

Bad shortcuts reveal the guardrails.

Invert the tempting mistake and the architecture becomes easier to see.

Retain the divergence · I091–I100 · 10 inverted shortcuts
  1. I091Bad idea: hide anything that times out. Inversion: never couple broken detection to hidden; uncertainty keeps all tags unchanged.
  2. I092Bad idea: retry 429 immediately until it works. Inversion: bounded host-aware cooldown and deferred checks respect remote limits.
  3. I093Bad idea: mark every 403 broken. Inversion: distinguish bot visibility from visitor availability and surface access-denied evidence.
  4. I094Bad idea: permanently exempt manual broken tags. Inversion: successful checks remove them exactly as the agreed baseline allows.
  5. I095Bad idea: execute a script to prove its link works. Inversion: HTTP-only checks never execute downloaded code; script correctness is not link availability.
  6. I096Bad idea: rewrite URLs to whatever redirected successfully. Inversion: report final locations but leave destination changes to maintainers.
  7. I097Bad idea: make a network check a deployment prerequisite. Inversion: publish the valid directory even during external outages; reachability work is independent.
  8. I098Bad idea: force-push a freshly serialized map over human edits. Inversion: source-SHA and bot-branch ownership guards protect concurrent work without link-tag ownership metadata.
  9. I099Bad idea: clear broken whenever a scan lacks a failure result. Inversion: only positive reachable evidence clears it; missing data is unknown/skipped.
  10. I100Bad idea: push with GITHUB_TOKEN and assume Pages ran. Inversion: human merge or an explicit documented dispatch path, with deployment run status checked.

Decision Tree Mapping / proof and alternative bundles

Choose what “automatic” should mean.

The detection policy and the publication policy are independent choices. More automation is not automatically more evidence.

Policy proof, later

Deterministic local HTTP: retries, redirects, budgets; both tagged and untagged unknown preservation; manual/case-insensitive broken recovery; hidden/disabled immutability.

Publication proof, later

Nested source fidelity, JSON/YAML and idempotence; changed SHA, cancellation, publisher failure; actual bot PR validation and merge-to-Pages smoke test.

Retain the divergence · I101–I110 · 10 proof and bundle candidates
  1. I101Verify 404/404 adds broken, 404/200 clears it, and 404/timeout leaves it unchanged using deterministic local HTTP responses.
  2. I102Verify 401/403/429/503, DNS/TLS failure, redirect loop, and exhausted budgets leave both tagged and untagged entries unchanged.
  3. I103Verify a normal redirect to 200 clears broken, redirects to confirmed 404 add it, and HTML-only forwarding does not pretend to be HTTP traversal.
  4. I104Verify nested YAML comments, JSON, URL-string conversion, case variants, unrelated tags, and repeated-run idempotence against a small map.
  5. I105Verify hidden and disabled tags never change, while their entries remain eligible for broken updates.
  6. I106Verify changed main SHA, publisher failure, and cancellation produce no stale source write or deployment.
  7. I107Prototype bundle A: daily/manual + repeated 404/410 only + human-merged GITHUB_TOKEN PR; low setup, deliberate publication delay.
  8. I108Prototype bundle B: same classification + GitHub App + tested auto-merge; unattended publishing at a higher setup cost.
  9. I109Prototype bundle C: recurrent transport/5xx failures also mark broken after multi-run evidence; broader outage coverage at the cost of durable history and flapping policy.
  10. I110Prototype bundle D: report-only health checks without tag edits; simplest diagnostics, but it does not deliver automatic broken-tag upkeep.

Synthesis / the central connection

Unknown belongs in the evidence.
Not in the link.

The source stores only the checker’s broken annotation—not a new unknown tag. Ambiguous or incomplete observations preserve previous state. This trades stale annotations for fewer false positives, and the report must make that trade visible.

Evidence → decision

“Latest check” means the latest completed bounded evaluation, not every failed request. Two matching gone statuses confirm disappearance within a run; a 2xx can clear even a manual broken tag.

Decision → source

Only exact broken changes. Unknown/skipped keep tags unchanged; hidden is never set from broken, and disabled stays user-controlled. No per-link ownership tracking is needed.

Source → publication

A source-SHA guard and bot-branch guard protect human work. A reviewed source diff takes the established PR → merge → Pages path, rather than deploying an uncommitted mutation.

The blind spot is real.

Repeated-404/410 detection catches explicit HTTP disappearance, not all sustained network or server outages. A permanently dead DNS name, persistent TLS failure, or repeated 503 may remain untagged indefinitely. An already-broken link may also keep its stale annotation under unknown evidence. Broader semantics require an explicit decision about evidence and persistence.

Proposed v1 boundary: no cross-run counters, durable health cache, ownership metadata, automatic hiding/disabling, content scraping, browser execution, per-domain rule engine, or downloaded script execution. A 2xx proves observed HTTP reachability—not useful content, complete download, or script correctness.

Coach’s landing: Bundle A, after the state-tag baseline and hidden migration. Trial report-only first; tune unmeasured budgets; enable one human-merged source-edit bot PR; revisit unattended merge and broader evidence only afterward.
