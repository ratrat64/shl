# Landing checks and independent evidence

Accessed 2026-10-27. Research lead fetched these sources during this run. No prototype or deployed Pages experiment was run. Verification here concerns evidence, not implementation acceptance.

## External sources

1. MDN contributors, **JavaScript frameworks and libraries**, last modified 2026-08-13: https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/Frameworks_libraries . A request to the old Svelte_getting_started URL redirected to this overview, so it is **not** Svelte-specific tutorial evidence. It lists Svelte and Vue as alternative frameworks and stresses that these are not endorsements/rankings. Medium, single-source ecosystem signal; no longitudinal maintenance/popularity conclusion.
2. MDN contributors, **Framework main features**, last modified 2025-04-11: https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/Frameworks_libraries/Main_features . Excerpts: components describe “external properties”, “internal state” and “events”; frameworks make rendering decisions so “you typically don't interact with the DOM yourself”. This independently corroborates the generic capability premise behind component adoption, alongside Vue/React/Svelte's own docs. Class: architectural pattern, verified narrowly. It does not prove any candidate reduces shl maintenance. Older implementation examples were not used for current compatibility or comparative performance.
3. Cloudflare, **SvelteKit**, last updated 2026-04-21: https://developers.cloudflare.com/pages/framework-guides/deploy-a-svelte-kit-site/ . Describes Svelte as a compiler and Kit as its application framework, independently corroborating that distinction. Mentions static adapter output separately from the server adapter. Its phrase “no server-side rendering” for adapter-static is ambiguous about build-time rendering; defer to Svelte's explicit prerender documentation rather than infer absence of static HTML. Class: capability/architecture, compiler-vs-app distinction verified narrowly; exact tool compatibility unverified. No Cloudflare deployment configuration is a GitHub Pages recipe. The six-month-old guide is not sufficient current ecosystem-health evidence.
4. Svelte project, **Imperative component API**, undated: https://svelte.dev/docs/svelte/imperative-component-api . Re-fetched relevant API directly: render requires server compilation and returns body/head; hydrate reuses Svelte SSR HTML. Confirms digest's wording. Single publisher, independently unverified; primitives do not prove Bun/toolchain compatibility.
5. Svelte project, **Single-page apps**, undated: https://svelte.dev/docs/kit/single-page-apps/llms.txt . Exact caveat: fallback “will always contain absolute asset paths … regardless of the value of paths.relative”. Build-time prerender “won't need a Node server” at deployment. Confirms the load-bearing fallback limitation in the first digest; no independent arbitrary-prefix experiment. Mark unverified under the strict independent-publisher rule, despite strong primary documentation.
6. Astro project, **View transitions**, undated: https://docs.astro.build/en/guides/view-transitions/ . Re-fetched: body replaced; matching transition:persist elements carried over; island state retained but props update unless persist-props. Default client navigation executes new scripts and inline scripts may repeat. This matters because shl's current navigation deliberately strips fetched scripts. Single publisher; no equivalence claim.
7. Astro maintainers, **router.ts**, undated rolling main source: https://raw.githubusercontent.com/withastro/astro/main/packages/astro/src/transitions/router.ts . `fetchHTML` validates media type, reads text and does not test `res.ok`; `defaultLoader` parses it and requires the incoming transition-enabled marker. Therefore it is incorrect to claim this retrieved implementation categorically rejects HTTP 404. Source also calls runScripts after the swap. This closes an evidence gap in the Astro digest without establishing full recovery or released-version behavior. Class: implementation observation; primary-documented, independently unverified. A rolling main branch is not a pinned release; verify again before implementation.

## Checks and outcomes

- Generic components/state/event/render responsibility has independent corroboration (MDN plus vendor docs); net productivity and ranking remain analyst hypotheses.
- Static output fits GitHub Pages' static hosting model (GitHub plus Astro/Nuxt guides); this does not validate each framework's application routing.
- Svelte's compiler/application-framework distinction has independent corroboration (Cloudflare plus Svelte); this does not independently verify a version pair.
- All decisive **comparative** cells (migration savings, exact identity, portable-base recovery) lack independent executed evidence. Keep medium/low confidence, sensitivity analysis and a pilot gate; do not invent a decisive benchmark.
- Astro's stock routing is more capable than a blanket “404 unsupported” objection. The remaining concerns are unknown-base bootstrap, exact persistence/lifecycle policy, fetched-script execution and custom integration, not demonstrated inability to parse a 404 response.
- No current incident/post-mortem cohort or longitudinal repository-health study was acquired within this focused run. Do not turn missing experience evidence into reliability claims or old bug reports into current failures.
- First-pass dimensions stop at documented-capability coverage. Follow-up stops at the approved depth cap; compatibility, implementation cost and deployed behavior remain explicit open questions.
